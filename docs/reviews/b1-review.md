# B1 review (branch show-dont-hide, commits e489137, 9838637, aee8e89)

Verdict: CHANGES NEEDED (two Medium findings, 1 and 2; the rest are Low or notes).

Checked: the design doc, the B1 report and ledger, migrations 0034 to 0040 against the versions they replace (0006, 0014, 0023, 0024, 0030, 0031, 0032), every changed test, the TS diff, and main's consumers of each changed RPC.

## Findings

1. **Medium, privacy. `supabase/migrations/0036_visible_claims.sql:16-19`.** Since 0024, masked claims (artist-only or anonymous) show only the UTC day in `claimed_at`. The new `held_days` is `floor((now - c.claimed_at)/86400)` on the exact timestamp, though, so anyone can poll it and see the minute it ticks over. That minute is the exact claim time, which 0024 hides on purpose. `dropped_after_days` and `dropped_early` (the 13d23h boundary) also leak the exact interval for masked claims. Fix: for non-public rows, compute all three from `date_trunc('day', claimed_at, 'UTC')` (and the drop day) and compare day counts. Add a test with a masked claim made at 23:00 UTC.
2. **Medium, security and correctness. `0038_public_artist_status.sql:4-8` (`is_verified_owner`).** The function checks `verified_at is not null` only. Nothing clears `verified_at` (0017:86 only sets status to 'delisted'), so the owner of a delisted page keeps counting as 2 submitters in `submit_artist` (0039:61) and in the public counts, and can still report with no age wait (0040:15). The brief asks that a page that is later delisted or unverified stop counting. Fix: add `and a.status <> 'delisted'`, and decide whether 'disputed' should count too. Add a pgTAP case.
3. **Medium, product (report wording). `0040_report_verified_owner.sql:13-18`, `src/lib/song-rules.ts:93`.** The database never raises `account_too_new`. A report from an account under 3 days is stored and the user sees the normal success, but no dispute starts, so the mapped message is dead code. If B2 shows "Reports open when your account is 3 days old" before the report, it is misleading: the user can still send one and is told it went through. Recommendation: reject outright. Before the insert, `if not (old or is_verified_owner) then raise exception 'account_too_new'`. That makes the message true. Main's ReportButton shows its generic error for unknown codes, so this is upgrade-safe. If you keep the soft path, the wording should be "Thanks. Reports from accounts under 3 days old are recorded but don't put a page under review." (Note: hard rejection is a departure from 0022 and 0031 behaviour; Brian should confirm.)
4. **Low, spec conflict. Decision 5 vs `0037_base_points.sql:5,36`.** The base point has no age rule, so a 1-day-old account earns 1 point at once (tested at show_dont_hide.test.sql:104). The spec text "New accounts see 'You can start earning in N days'" then contradicts the board. B2 needs wording such as "growth points start in N days". Flag it to Brian.
5. **Low, correctness. `0037:37`.** `at_risk` for a past season uses `c.dropped_at is null`, which is today's state, not the state at season end. A late-February claim that was still active at the end of February but dropped in March shows at_risk = false for February, and one still active today shows true. Use `(c.dropped_at is null or c.dropped_at >= v_end) and c.claimed_at > v_end - 14 days`. The `where` clause already guarantees the first part, so this is mainly about intent and consistency. Also: re-running the refresh for any season before 0037 adds +1 per claim to it after the fact (R26 changes only on the day-1 cron, which refreshes the previous month). Push before 1 Nov so October is never mixed, and record in the ledger that older seasons should not be refreshed by hand.
6. **Low, semantics. `0037` at_risk definition.** In the current season, a dropped claim loses all of its points whatever its age (R26), so "At risk" (only claims under 14 days old) understates what dropping costs. It matches decision 5 as written. B2 copy should not say that only these points are lost.
7. **Low, privacy. `0038:20-22` and `0039:76`.** The weighted `support_points` and `scouts_submitted` let someone infer that a submitter of a pending page owns a verified page (for example, 2 support from 1 submission). It reveals no identity. Acceptable; note it.
8. **Low, abuse surface. `0038:17`.** Pending pages are now readable by address with a submitter-supplied https `source_url`. Before, 3 scouts gated public visibility. B2 must render the link with `rel="nofollow ugc noopener"`. Confirm the URL is the canonicalised platform URL and not free text.
9. **Low. `src/lib/verify-artist.ts` (`getVerificationCodeInfo`).** `issuedAt` comes from the newest row, but 0032 measures expiry from `min(checked_at)` for that code. These are the same today because a code gets one issue row, but use the earliest row to stay faithful. The `state.issued ?? Date.now()` fallback can show a later expiry than the database enforces. The issue time is also set from the app clock (`checked_at` explicit), so app/DB clock skew moves the true expiry. Prefer the DB default and read the value back.
10. **Low, tests.** There is no test for `claim_unlocks_at` returning null for another user's claim, the `claim_locked` DETAIL format, a delisted verified owner (finding 2), masked-claim `held_days` precision (finding 1), or past-season at_risk. The anon-handle test (boards.test.sql) only checks two handles; assert that every masked row is 'Anonymous scout'. No new concurrency script was added. That is acceptable because the locking order in `submit_artist` is unchanged (artist row `for update`, then insert, then a weighted sum over committed rows). `artist_submissions` has `on conflict do nothing`, so one account cannot count twice (tested at show_dont_hide.test.sql:41-42).

## Verified OK

- `search_path = public, pg_temp` is pinned on every new or changed function (0034 to 0040), including the non-definer constants.
- Grants: `is_verified_owner` is service_role only. `claim_unlocks_at` and `drop_claim` are authenticated only. `public_artist_status`, `artist_founders`, `scout_historical` and `pending_artists_public` are anon and authenticated. `season_board` grants are as before, and `my_season_standing` is authenticated only. The `qualified_*` grants are kept by `create or replace`. The only new anon-callable functions are `public_artist_status` and the two constants, which are harmless.
- `public_artist_status` returns no scout, submitter or reporter columns, and for delisted pages only name, slug and status.
- `artist_founders` and `scout_historical` still mask handles, and others see only public claims in history.
- The 3-day lock boundary is correct (`v_unlock > now()`, so exactly 72h is allowed; tested at 71h59m and 72h). The DETAIL holds only the unlock time. No other path ends a claim: there is no update policy on `claims`, and `drop_claim` is the only setter of 'historical'.
- Account age: there are no live `7 days` age rules left. The remaining hits are in superseded definitions (0002, 0003, 0014, 0023, 0022 and 0031 `report_artist`), all replaced by 0034 and 0040, including `qualified_referrals` (0003).
- `season_board` and `my_season_standing` append a column. Ranks use `rank()` over all entrants, so ties share a rank (tested). `refresh_season_scores` is idempotent: it deletes and re-inserts the per-claim rows and upserts the scores under the advisory lock.
- Upgrade safety: every RPC whose return type changed only gains columns and keeps the old names. Main reads them by name (`artist/[slug]`, `scout/[handle]`, `leaderboard`, `discover`). Each drop and recreate runs inside one migration transaction, with grants restored. The display differences are as the ledger lists.
- Test edits in the existing pgTAP and vitest files follow from the rule changes (+1 base point, 3 days, immediate visibility, 72h lock) and are not weakened.
